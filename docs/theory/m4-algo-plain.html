Модуль 4 — Алгоритмы на пальцах

Конспект обновлён 2026-06-18

Зачем эта заметка

Обычный конспект Модуля 4 не зашёл — теория повисла в воздухе. Эта заметка — то же самое, но с другой стороны: сначала зачем оно нужно на примерах из жизни, потом образ, потом код. Когда станет понятно — пойдёшь в формальный Python — Модуль 4 Алгоритмическое мышление как в справочник.

Правило: не двигайся дальше следующего раздела, пока в текущем не сможешь объяснить материал «на пальцах» вслух.

Зачем это вообще нужно

У тебя есть программа, которая работает. Вопрос: будет ли она работать через год, когда данных станет в 1000 раз больше?

  • Сайт магазина. 100 товаров — быстро. 1 000 000 товаров — за 30 минут открывается. Почему?
  • Анализ данных. На 1000 строк — секунда. На миллион — час. Где зашили косяк?

Ответ почти всегда один: код был написан без понимания, как он растёт с увеличением данных. Программист, который этого не понимает — пишет код, который ломается при росте нагрузки.

Модуль 4 — про три инструмента, которые дают это понимание:

  1. Big O — язык, чтобы сказать «эта функция при 1М данных работает в 10000 раз быстрее, чем та»
  2. Рекурсия — способ написать функцию, которая обходит вложенные структуры неизвестной глубины (каталог папок, дерево комментариев, JSON с подкатегориями)
  3. Бинарный поиск — способ найти элемент в большом отсортированном списке не за 1 000 000 шагов, а за 20

Это не математика ради математики. Это инструменты практики, без которых на собеседовании сразу отказывают, а в работе пишешь медленные программы.

ЧАСТЬ 1 — Big O

Образ: поиск ключей в квартире

Ты потерял ключи. Сколько времени займёт поиск?

Сценарий A. Ты помнишь, что они на столе. Подходишь — берёшь. 1 действие. Сколько бы ни было вещей в квартире — это всегда 1 действие. Это O(1) — «константа».

Сценарий B. Ты не помнишь где. Идёшь по комнатам и осматриваешь каждый предмет. Если предметов 100 — до 100 проверок. Если 10 000 — до 10 000. Время растёт прямо с количеством предметов. Это O(n) — «линейно».

Сценарий C. Ты решил не просто искать ключи, а сравнить каждый предмет с каждым на похожесть. 100 предметов → 100 × 100 = 10 000 сравнений. 10 000 предметов → 100 000 000 сравнений. Это O(n²) — «квадратично». Очень плохо при росте.

Сценарий D. У тебя отсортированный картотека: каждый раз делишь стопку пополам. 1 000 000 карточек → 20 делений (потому что 2²⁰ ≈ 1М). Это O(log n) — «логарифмически». Очень хорошо.

Главное, что нужно понять

Big O — это не точное число операций. Это скорость роста числа операций при увеличении данных.

Запись Что значит на пальцах На 1 000 000 элементов
O(1) Работает мгновенно, не зависит от размера 1 шаг
O(log n) Очень быстро, рост почти незаметный ~20 шагов
O(n) Терпимо. Идём по каждому элементу 1 000 000 шагов
O(n log n) Норма для сортировки ~20 000 000 шагов
O(n²) Боль. На больших данных — катастрофа 1 000 000 000 000 шагов

Как читать код на Big O — три правила

Правило 1. Один цикл по списку из n элементов → O(n).

for x in lst:        # пробежали n раз
    print(x)

Правило 2. Цикл внутри цикла по тем же данным → O(n²).

for i in lst:        # n раз
    for j in lst:    # внутри ещё n раз
        print(i, j)  # итого n × n = n²

Правило 3. Два цикла подряд (не вложенных) → всё равно O(n).

for x in lst:        # n шагов
    print(x)
for x in lst:        # ещё n шагов
    print(x)
# Итого 2n. Но 2 — это константа, отбрасываем. O(n).

Слабая точка: «два цикла подряд» интуитивно кажется как «много», но на самом деле это всё ещё O(n), а не O(n²). Вложенность важна, а не количество циклов.

Почему set — это магия

"яблоко" in ["яблоко", "груша", "слива"]  # O(n) — идём по списку
"яблоко" in {"яблоко", "груша", "слива"}  # O(1) — мгновенно

Set устроен изнутри как хэш-таблица. Когда ты говоришь x in set, Python не идёт по элементам — он сразу прыгает в нужную ячейку памяти. Это всегда одно и то же количество операций, неважно сколько элементов в set: 10 или 10 миллионов.

Главный практический вывод модуля:

Если в твоём коде есть for ... in list и внутри другой for ... in list — почти всегда можно ускорить, превратив один из списков в set.

Конкретный пример «было/стало»

# БЫЛО — O(n²): для каждого элемента ищем дубликат по всему списку
def has_duplicate(lst):
    for i in range(len(lst)):
        for j in range(i + 1, len(lst)):
            if lst[i] == lst[j]:
                return True
    return False
# На 100 000 элементов — несколько минут.

# СТАЛО — O(n): идём один раз и запоминаем виденные в set
def has_duplicate(lst):
    seen = set()
    for x in lst:
        if x in seen:    # O(1) — мгновенная проверка
            return True
        seen.add(x)
    return False
# На 100 000 элементов — миллисекунды.

ЧАСТЬ 2 — Рекурсия

Главное недоразумение, которое мешает понять

Когда говорят «функция вызывает саму себя» — кажется, что одна и та же функция как-то заглядывает внутрь себя. Это неправильная картинка.

Правильная картинка: каждый раз, когда ты пишешь имя функции со скобками — Python запускает новую отдельную копию этой функции. С нуля. Со своими переменными. С собственным значением n.

Если функция в своём теле пишет своё имя со скобками — Python запускает ещё одну копию. И ещё. И ещё. Это и есть рекурсия. Не одна функция, заглядывающая в себя — а много копий одной и той же функции, стоящих друг за другом.

Запомни эту фразу — она ключевая ко всему остальному:

Каждый вызов = новая копия со своим n. Старая копия в это время стоит на паузе на той строке, где запустила новую.

Базовый пример — самый важный в этом разделе

Посмотри на код. Разбери его сам, потом сверься с разбором ниже.

def rec_func(n):
    if n < 4:
        print(n)
        rec_func(n + 1)
        print(n)

rec_func(1)

Что выведет? Не угадывай — попробуй проследить.

. . .

Ответ: 1 2 3 3 2 1

Почему так — сейчас разберём по шагам.

Разбор по копиям

Запускаем rec_func(1). Python создаёт копию №1 функции, в её локальной переменной n = 1.

КОПИЯ №1 (n=1):
    if 1 < 4:        ← да
        print(1)     ← в консоль выводится "1"
        rec_func(2)  ← запуск новой копии! Копия №1 ставится на паузу
                       прямо на этой строке.
        print(1)     ← НЕ выполняется пока. Дойдём сюда, когда копия №2 завершится.

Python запустил rec_func(2). Создаётся копия №2, у неё свой n = 2. Копия №1 ждёт.

КОПИЯ №2 (n=2):
    if 2 < 4:        ← да
        print(2)     ← в консоль выводится "2"
        rec_func(3)  ← запуск ещё одной копии! Копия №2 ставится на паузу.
        print(2)     ← подождёт.

Создаётся копия №3, у неё n = 3. Копии №1 и №2 ждут.

КОПИЯ №3 (n=3):
    if 3 < 4:        ← да
        print(3)     ← в консоль выводится "3"
        rec_func(4)  ← запуск ещё одной копии! Копия №3 ставится на паузу.
        print(3)     ← подождёт.

Создаётся копия №4, у неё n = 4.

КОПИЯ №4 (n=4):
    if 4 < 4:        ← НЕТ. В if не заходим.
                     ← тело функции закончилось. Копия №4 завершается.

Копия №4 ничего не вывела и закрылась. Это и есть тот самый «момент остановки» — базовый случай. Без него копии создавались бы бесконечно (rec_func(5), rec_func(6), ...). А if n < 4 поставил предел.

Теперь начинается подъём. Копия №3 ждала на строке rec_func(4). Эта копия завершилась — значит копия №3 «просыпается» и идёт дальше:

КОПИЯ №3 продолжает с того места, где остановилась:
        print(3)     ← в консоль выводится "3"
                     ← тело закончилось. Копия №3 завершается.

Копия №2 ждала на rec_func(3). Просыпается:

КОПИЯ №2 продолжает:
        print(2)     ← в консоль выводится "2"
                     ← тело закончилось. Копия №2 завершается.

Копия №1 ждала на rec_func(2). Просыпается:

КОПИЯ №1 продолжает:
        print(1)     ← в консоль выводится "1"
                     ← тело закончилось. Копия №1 завершается.

Программа закончена. В консоли по порядку появилось: 1 2 3 3 2 1.

Главные выводы из этого примера

1. Спуск и подъём. В функции с рекурсивным вызовом посередине код делится на две части:

def rec_func(n):
    if n < 4:
        print(n)           # ← СПУСК: выполняется ДО создания новой копии
        rec_func(n + 1)
        print(n)           # ← ПОДЪЁМ: выполняется ПОСЛЕ возврата из копии

Спуск идёт сверху вниз по копиям: №1 → №2 → №3. Подъём идёт снизу вверх: №3 → №2 → №1. Поэтому вывод симметричный: на спуске 1 2 3, на подъёме 3 2 1.

Если уберёшь print до вызова — увидишь только подъём: 3 2 1. Если уберёшь print после вызова — увидишь только спуск: 1 2 3.

2. У каждой копии — своя локальная n. Когда копия №1 на подъёме делает print(n) — она печатает свою n = 1, а не последнюю. Старые копии никуда не делись, они просто стояли на паузе.

3. Условие в if — это тормоз. Без него копии плодились бы вечно и Python бы упал. Это «дно», в которое упирается рекурсия.

Терминология (теперь, когда уже понятно)

То, что мы только что сделали, формально называется так:

  • Базовый случай (база) — условие, при котором функция НЕ запускает новую копию себя. В нашем примере это «n < 4 ложно» — тогда в if не заходим и копия просто закрывается.
  • Рекурсивный шаг — место, где функция вызывает саму себя с другим аргументом (обычно ближе к базе). В нашем примере: rec_func(n + 1) — каждая копия передаёт следующей n больше на единицу.

Правило: в каждой рекурсивной функции должны быть обе вещи. База — иначе бесконечные копии. Шаг к базе — иначе ты до базы никогда не дойдёшь.

Усложнение №1 — функция возвращает значение

До сих пор копии просто печатали в консоль. А если копия должна вернуть число?

Пример: посчитать сумму чисел от 1 до n.

def summa(n):
    if n == 0:               # БАЗА: сумма от 1 до 0 это просто 0
        return 0
    return n + summa(n - 1)  # ШАГ: n + сумма от 1 до n-1

Разбор summa(3):

КОПИЯ №1 (n=3):
    return 3 + summa(2)
    ↑ чтобы вернуть результат, нужно дождаться, что вернёт копия №2.
      Копия №1 стоит на паузе.

    КОПИЯ №2 (n=2):
        return 2 + summa(1)
        ↑ ждём копию №3.

        КОПИЯ №3 (n=1):
            return 1 + summa(0)
            ↑ ждём копию №4.

            КОПИЯ №4 (n=0):
                return 0                ← БАЗА. Возвращает 0 в копию №3.

        КОПИЯ №3 получает 0:
            return 1 + 0 = 1            ← возвращает 1 в копию №2.

    КОПИЯ №2 получает 1:
        return 2 + 1 = 3                ← возвращает 3 в копию №1.

КОПИЯ №1 получает 3:
    return 3 + 3 = 6                    ← это окончательный ответ.

Главное в этом примере: строчка return n + summa(n - 1) означает «верни сумму этого n и того, что вернёт меньшая копия». Ты доверяешь, что копия summa(n-1) правильно посчитает свою часть. Тебе не нужно думать «а как именно она это сделает» — она такая же функция, ты её и пишешь. Ты просто веришь.

Это и называется «акт веры» в рекурсии. Когда внутри функции ты пишешь вызов самой себя — относись к нему как к чёрному ящику, который вернёт правильный ответ для меньшей задачи. Без этой веры рекурсию не написать — мозг будет пытаться развернуть все вызовы у себя в голове и сломается.

Усложнение №2 — данные сами вложенные

Иногда рекурсия — единственный удобный способ, потому что данные сами по себе рекурсивны. Каждый узел дерева содержит такие же узлы.

employees = {
    "name": "CEO",
    "children": [
        {"name": "CTO", "children": [
            {"name": "Dev1", "children": []},
            {"name": "Dev2", "children": []},
        ]},
        {"name": "CFO", "children": [
            {"name": "Acc1", "children": []},
        ]},
    ]
}

Сколько уровней? 3. А могло бы быть 10 или 100. Циклом ты не знаешь сколько for вкладывать. Рекурсия — знает:

def count(node):
    total = 1                       # сам этот человек
    for child in node["children"]:
        total += count(child)       # доверяем: count посчитает поддерево
    return total

count(employees)  # 6

База здесь спрятана: если children пустой — цикл for просто не выполнится, и функция вернёт 1 (только сам узел). Никакой новой копии не создаётся — рекурсия останавливается естественно.

Главные две ловушки

Ловушка №1 — забыть базу

def factorial(n):
    return n * factorial(n - 1)   # нет условия выхода

Копии создаются бесконечно. Через ~1000 копий Python обрывает программу: RecursionError: maximum recursion depth exceeded.

Лечение: первой строкой функции всегда пиши if <база>: return <готовый ответ>. Только потом — рекурсивный вызов.

Ловушка №2 — шаг не приближает к базе

def bad(n):
    if n == 0:
        return 0
    return bad(n)       # вызов с тем же n — копии плодятся с одинаковым n

База есть, но мы к ней никогда не придём — n не меняется.

Лечение: в рекурсивном вызове аргумент должен быть ближе к базе, чем у текущей копии. Чаще всего: n - 1, n // 10, s[1:], node["children"].

ЧАСТЬ 3 — Бинарный поиск

Образ: игра «угадай число»

Я загадал число от 1 до 100. Ты угадываешь, я говорю «больше» или «меньше».

Глупая стратегия: называть 1, 2, 3, 4... В худшем случае — 100 попыток.

Умная стратегия: называть всегда середину оставшегося диапазона. - Назвал 50. «Больше» → теперь ищу в 51-100 - Назвал 75. «Меньше» → теперь ищу в 51-74 - Назвал 62. «Больше» → теперь ищу в 63-74 - ...

Каждый раз диапазон сокращается вдвое. Из 100 чисел дойдёшь до ответа за 7 попыток (потому что 2⁷ = 128 ≥ 100). Из 1 000 000 — за 20.

Это и есть бинарный поиск.

Главное условие, без которого не работает

Список должен быть отсортирован.

Если список не отсортирован — стратегия «делить пополам» не работает, потому что нельзя сказать «искомое — слева или справа от середины».

Алгоритм пошагово

Есть отсортированный список и нужно найти target.

1. Установи две границы: left = 0, right = последний индекс
2. Пока left <= right:
   - Найди середину: mid = (left + right) // 2
   - Если lst[mid] == target — нашли, вернуть mid
   - Если lst[mid] < target — искомое правее, сдвинь left = mid + 1
   - Если lst[mid] > target — искомое левее, сдвинь right = mid - 1
3. Если вышли из цикла — нет такого элемента, вернуть -1

def binary_search(lst, target):
    left, right = 0, len(lst) - 1
    while left <= right:
        mid = (left + right) // 2
        if lst[mid] == target:
            return mid
        elif lst[mid] < target:
            left = mid + 1       # target правее середины
        else:
            right = mid - 1      # target левее середины
    return -1

Прогон на примере

binary_search([1, 3, 5, 7, 9, 12, 15, 18, 21, 24, 27, 30], 21)

Шаг left right mid lst[mid] Действие
1 0 11 5 12 12 < 21 → ищем правее, left = 6
2 6 11 8 21 равно! → return 8

Два шага вместо 12. На массиве из миллиона — было бы 20 шагов вместо миллиона.

Когда применять — узнать признаки

Бинарный поиск можно применить только когда: 1. Данные отсортированы (по ключу, по которому ищешь) 2. Есть прямой доступ к элементу по индексу (то есть это list, а не linked list или dict)

В Python это обычно отсортированный list чисел, строк, или список словарей, отсортированных по одному полю.

  3. Сколько шагов в худшем случае на массиве из 1024 элементов? А из 1 000 000?
  4. Что делать, если left > right?

Связка трёх тем

Эти три инструмента работают вместе:

  • Big O — даёт язык, чтобы сказать «бинарный поиск это O(log n), а линейный — O(n)»
  • Бинарный поиск — конкретный пример того, как алгоритм работает за O(log n)
  • Рекурсия — структурный приём, который часто даёт O(n) обход вложенных данных
