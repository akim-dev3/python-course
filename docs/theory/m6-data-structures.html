Модуль 6 — Структуры данных на пальцах

Конспект обновлён 2026-09-14

Зачем эта заметка

У Модуля 6 не было конспекта — только шпаргалка с синтаксисом. Шпаргалка отвечает на вопрос «как написать», но не на вопрос «почему именно эта структура». Здесь второе.

Главная мысль модуля одна: структура данных — это не хранилище, а выбор того, какая операция будет дешёвой. Список, стек, очередь и словарь хранят одно и то же. Разница в том, что у каждого дёшево, а что дорого.

Стек — «последний пришёл, первый вышел»

Образ. Стопка тарелок. Кладёшь сверху, берёшь сверху. Достать нижнюю, не сняв верхние, нельзя.

В Python стек — это обычный list: append() кладёт, pop() снимает. Оба с конца, оба за O(1).

stack = []
stack.append(1)   # положили
stack.append(2)
stack[-1]         # посмотрели верхний, не снимая → 2
stack.pop()       # сняли → 2

Когда стек — правильный ответ. Всякий раз, когда задача про вложенность или про «вернуться к предыдущему»:

  • скобки ([{}]) — открывающую надо запомнить, чтобы потом сверить с закрывающей
  • отмена действия (undo) — последнее действие отменяется первым
  • путь в файловой системе: .. означает «вернуться на уровень выше», то есть снять последнюю папку
  • вычисление выражения в постфиксной записи: операнды копятся, оператор снимает два последних

Общий признак: то, что положили последним, понадобится первым. Как только видишь это в условии — бери стек, не раздумывая.

Монотонный стек — приём, который не очевиден

Задача daily_temperatures: для каждого дня сказать, через сколько дней станет теплее.

Наивно — для каждого дня перебирать все следующие: O(n²). Приём: держать в стеке индексы дней, для которых ответ ещё не найден, и следить, чтобы температуры в стеке убывали. Приходит новый день — снимаем со стека все дни холоднее его: для каждого из них ответ найден, и это ровно текущий день.

Почему это O(n), а не O(n²): каждый день кладётся в стек ровно один раз и снимается ровно один раз. Двух проходов по одному элементу не бывает — значит операций порядка 2n.

Очередь — «первый пришёл, первый вышел»

Образ. Очередь в кассу. Встал в конец, обслужили с начала.

Здесь важная ловушка. Очередь напрашивается делать так:

q = []
q.append(1)      # это O(1), нормально
q.pop(0)         # а это O(n) — ЛОВУШКА

pop(0) вынимает элемент из начала списка, и все остальные элементы физически сдвигаются на одну позицию влево. На списке из миллиона элементов один такой вызов — миллион перемещений. Цикл из таких вызовов превращает O(n) алгоритм в O(n²).

Правильно — collections.deque (произносится «дэк», от double-ended queue). Он устроен так, что вставка и удаление с обоих концов стоят O(1):

from collections import deque

q = deque()
q.append(1)       # в конец, O(1)
q.popleft()       # из начала, O(1) — вот ради этого всё
q.appendleft(0)   # в начало, тоже O(1)

Когда очередь. Обработка «в порядке поступления»: задачи, события, уровни обхода. Плюс два неочевидных применения:

  • скользящее окно с быстрым удалением слева — окно растёт справа (append) и сжимается слева (popleft), ровно две операции deque
  • топологическая сортировка (can_finish_in_order): считаем, сколько у каждой задачи невыполненных зависимостей, кладём в очередь задачи с нулём зависимостей, обрабатываем и уменьшаем счётчики у зависимых. Если в конце обработали не все задачи — в графе цикл, порядок невозможен

Связный список — зачем он, если есть list

Честный ответ: в рабочем коде на Python — почти никогда. Встроенный list быстрее почти во всём, потому что лежит в памяти одним куском.

Учат его по двум причинам: это классика собеседований и это единственный простой способ прочувствовать, что такое ссылка на объект.

Устройство. Узел хранит значение и ссылку на следующий узел. Последний ссылается на None.

class Node:
    def __init__(self, value):
        self.value = value
        self.next = None

Обход всегда выглядит одинаково — этот шаблон стоит выучить как есть:

current = head
while current:
    ...            # что-то делаем с current.value
    current = current.next

Разворот списка — три указателя

Единственная по-настоящему хитрая операция. Разворачивать надо перелинковкой, не создавая новых узлов.

Проблема: как только мы напишем current.next = prev, мы потеряем ссылку на следующий узел — она была только в current.next. Поэтому её надо сохранить до перезаписи:

prev = None
while current:
    next_node = current.next    # сохранили, иначе потеряем
    current.next = prev         # развернули ссылку назад
    prev = current              # сдвинули оба указателя
    current = next_node
# prev теперь новая голова

Slow / fast — тот же приём, что в Модуле 5

Два указателя, но один идёт по одному шагу, второй по два.

  • Середина списка: когда быстрый дошёл до конца, медленный ровно посередине. Один проход вместо двух (сначала посчитать длину, потом пройти половину).
  • Цикл в списке: если список зациклен, быстрый рано или поздно догонит медленного — они оба ходят по кругу с разной скоростью. Если быстрый дошёл до None — цикла нет.

Это тот же slow/fast, что был на массивах в Модуле 5, только вместо i += 1 пишется node = node.next.

Хэш-таблица — почему in у множества мгновенный

Это самая полезная часть модуля для реальной работы.

Что происходит внутри dict и set. От ключа считается hash(key) — число. Это число превращается в индекс ячейки массива. Значение кладётся сразу в нужную ячейку — не перебирая остальные.

Отсюда главное следствие:

x in some_list   # O(n)  — перебирает элементы по одному
x in some_set    # O(1)  — считает хэш и смотрит в одну ячейку
d[key]           # O(1)  — то же самое

Разница не «немного быстрее», а качественно другая. На списке из 100 000 элементов проверка in перебирает до 100 000 элементов; на множестве — считает одно число.

Коллизия — когда два разных ключа попали в одну ячейку. Такое бывает, и структура умеет это разруливать, поэтому в худшем случае операция деградирует до O(n). На практике это почти не встречается, и O(1) считают честной оценкой (говорят «в среднем» или «амортизированно»).

Ключ должен быть хэшируемым, то есть неизменяемым: int, str, tuple — можно; list, dict, set — нельзя. Причина простая: если ключ изменить после вставки, его хэш станет другим, и найти его в таблице будет уже невозможно.

Сдвиг мышления, ради которого всё это

Многие задачи выглядят как «перебрать все пары» — то есть O(n²) с двумя вложенными циклами. Хэш превращает их в один проход.

Пример — two_sum. Найти два числа с суммой target.

Наивно: для каждого числа перебрать все остальные — O(n²). Через хэш: идём по списку один раз и на каждом числе x спрашиваем — «а встречалось ли мне раньше target - x?». Это вопрос вида «было / не было», а он у словаря стоит O(1):

seen = {}                        # значение → индекс
for i, x in enumerate(nums):
    if target - x in seen:
        return (seen[target - x], i)
    seen[x] = i

Общий признак: как только в задаче звучит «а было ли уже такое» — это хэш, а не второй цикл.

Ещё два узнаваемых применения:

  • Группировка по вычисляемому ключу (group_anagrams): ключом делается не сам объект, а его нормальная форма. У анаграмм "eat" и "tea" отсортированные буквы совпадают → один ключ → одна группа.
  • Префиксные суммы (subarray_sum_equals_k): в словарь копятся суммы префиксов. Если текущая сумма минус k уже встречалась N раз — значит есть N подмассивов с суммой k, заканчивающихся здесь. Работает и с отрицательными числами, где два указателя из Модуля 5 уже неприменимы.

Что выбрать — одной строкой

Признак в условии Структура
вложенность, парность, «вернуться назад», undo стек (list)
«в порядке поступления», обход по уровням, окно очередь (deque)
«было / не было», группировка, счётчики set / dict
нужны ссылки и перелинковка (собеседование) связный список

И главный красный флаг: если пишешь два вложенных цикла — остановись и спроси, нельзя ли заменить внутренний на set или dict. Чаще всего можно.
